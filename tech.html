04 // Intelligence Layer

Agent Runtime

Die Runtime besteht aus mehr als einem Modell: Ziel, Tools, persistentes Wissen und Verifikation. Entscheidend ist ihre Resilienz gegen Androids Speicherverwaltung – Kills verhindern lässt sich nicht immer, aber ein einzelner Kill darf nicht alles stoppen.

ReasoningHermes plant, pi baut

Im Multi-Agent-Workflow plant Hermes, pi implementiert und Hermes verifiziert unabhängig.

ContextHolographic Memory

HUNTERs Memory fasst nur 2.200 Zeichen — deshalb habe ich ein Holographic-Gedächtnis ergänzt: eine lokale SQLite-Datenbank ohne Limit. Dazu fünf Sicherheitsschichten, damit nichts verloren geht: AGENTS.md bei jedem Erwachen, die Obsidian-Vault als Gehirn, Skills als prozedurales Wissen und eine Volltextsuche über alle vergangenen Gespräche. Ein Background-Review lernt aus den Fehlern des Systems — reaktiv, nicht proaktiv. Den Unterschied habe ich beim Betrieb selbst erfahren.

Agent // SurvivalSurvival Layer

Ich habe drei Schichten gebaut, damit HUNTER Androids Speicherverwaltung übersteht. Erstens: ein externer Cron-Tick aus Termux, der unabhängig vom internen Scheduler-Thread feuert — stirbt der Ticker, laufen die Jobs trotzdem. Zweitens: ein semantischer Watchdog, der nicht fragt „läuft der Prozess?“, sondern „arbeitet das System wirklich?“ — Herzschlag, letzter erfolgreicher Tick, überfällige Jobs, mit 30-Minuten-Cooldown gegen Restart-Loops. Drittens: bewusste RAM-Disziplin — Browser nur manuell, kurz, bei genug freiem Speicher.

Gemessen: 83+ Stunden Uptime, 0 OOM-Kills seit dem Fix am 28.08. Ehrliche Grenze: Bei Speicherdruck gewinnt Android immer. HUNTER ist darauf gebaut, Kills zu überstehen — nicht sie zu verhindern.
